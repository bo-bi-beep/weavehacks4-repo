# WeaveHacks 4 offline handbook

Offline summary of the participant handbook.

Source: https://wandbai.notion.site/WeaveHacks-4-participant-logistics-367e2f5c7ef380e7aa9ffb30e7055d7d

Last reviewed locally: 2026-06-06.

## Quick facts

- Venue: `400 Alabama Street`. Ring the callbox if the door is closed.
- Access: registered and approved participants only. Walk-ins are not accepted.
- Team size: solo is allowed; teams can have up to `5` members.
- Food: Saturday breakfast, snacks, dinner. Sunday breakfast and lunch.
- Office access: use any area not marked staff-only.
- W&B Weave project is required. Create / verify your W&B account before hacking.
- Public W&B project is not required, but the submission should still include a Weave link.
- In-person requirement: no remote participation. To be prize-eligible, participants must be present in person and must be there at some point on Saturday.

## Eligibility

Prize eligibility requirements:

- Code must be in an open GitHub repository so judges can inspect it.
- The project must be built during the hackathon.
- If the project connects to pre-existing work, clearly state what existed before; judging should focus on weekend work.
- Work must be primarily your team's own.
- The project must use W&B Weave.
- The team must create and demo the project in person.
- AI coding tools and agent loops are allowed.

## Submission

Submission deadline: `1:00 PM Sunday`.

The handbook mentions Cerebral Valley for submissions and judging details, and also mentions DevPost in one overview paragraph. Treat the live organizer announcement / final submission link as authoritative.

Submission should include:

- Unique team name.
- Names of all team members.
- Public GitHub repository link.
- Weave project / trace link.
- X and/or LinkedIn handles.
- Optional but strongly recommended: screen recording demo under 2 minutes, or explanatory images.
- A thorough project description:
  - 2-3 sentence summary.
  - What the project does and why it is useful.
  - How it is built.
  - RL environments, orchestration protocols, and agent app frameworks used, if any.
  - Every sponsor tool / protocol used and how it was used.

Live demos:

- Preliminary and final demos are strictly `3 minutes`.
- Demo should focus mostly on the working product.
- Use no more than 1-2 slides.
- Judges may ask 1-2 questions after the presentation.
- Make sure Zoom is installed or that browser sharing works: https://share.zoom.us

## Judging

Judging starts at `1:30 PM Sunday`.

Initial judging:

- Teams will be called and assigned a presentation room.
- Rooms are in the back of the venue along the wall.
- Presentations are `3 minutes`, with optional `2 minutes` for questions.

Final round:

- Organizers will announce 8 finalists.
- Finalists present in front of the live audience.
- Teams must be present; otherwise the next project may be selected.

Prize ceremony:

- Sponsor prizes are announced first.
- Grand prize winners are announced after sponsor prizes.

Criteria listed in the handbook:

- Impact potential / utility: does it address a real problem?
- Technical demo: does it work, and is it well engineered?
- Creativity: is the problem or approach new?
- Presentation and pitch: is it clearly presented and demonstrated?
- Multi-agent harness sophistication: does it meaningfully show a complex, effective multi-agent environment?
- Sponsor usage: did the team meaningfully use one or more sponsor tools?

## Practical advice from the handbook

- Pick team size carefully. Solo is possible, but a full 5-person team can be hard to coordinate.
- Use the event to meet collaborators and potential cofounders.
- Integrate components early instead of waiting until the final hour.
- Commit early and often so the project has checkpoints and judges can see it was built during the event.
- Use sponsor tools and onsite sponsor engineers.
- Make a short social post right after the hackathon while momentum is still high.
